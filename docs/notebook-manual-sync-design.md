# xPaste 记事本手动同步（稳妥版）设计方案

## 1. 背景

当前记事本目录同步机制在实际使用中存在不稳定问题。为了先交付一个“更稳妥、可控、可回滚”的方案，本设计优先实现**手动同步**能力，并补齐**云端文件管理**（查看/编辑/重命名/删除到回收站等）与**冲突处理**（提示是否强制替换，强制替换时云端自动备份）。

本方案以“文件为中心”：云端仅持久化文件与必要的元数据（回收站/备份记录），不把笔记内容再额外存入业务数据库（除非为了回收站/备份索引的可选表）。

## 2. 范围与目标

### 2.1 范围

- 管理当前登录用户在云端的“记事本文件空间”（Markdown 与附件文件，及其他同步目录内的普通文件）。
- 客户端支持：
  - 云端文件：查看、下载、编辑（文本）、重命名、删除（进入回收站）、回收站管理（查看/还原/彻底删除）。
  - 手动同步：将云端文件手动下载到本地同步目录；将本地选中/全部文件手动上传到云端。
  - 冲突提醒：当上传/下载会覆盖对端的不同内容时，弹窗提示“取消/跳过”或“强制替换”。
  - 强制替换策略：**覆盖云端前自动生成备份**（云端侧），确保可恢复。

### 2.2 目标

- 稳妥：任何“可能覆盖/丢失数据”的动作都有显式提示与可恢复机制（回收站/备份）。
- 可控：同步由用户触发、可看到计划与进度、可逐个处理冲突。
- 最小侵入：尽量复用现有鉴权与存储路径规则（`services/sync-api` 现有 `/notes/*` 与 `/uploads/file` 的用户隔离方式）。

### 2.3 非目标（本轮不做）

- 文件系统级自动监听（watcher）与实时增量队列的“自动同步”。
- 多端实时一致性（强一致）与复杂的三方合并（merge）。
- 对任意二进制文件的在线编辑（仅支持文本类编辑）。

## 3. 现状梳理（与本设计的关系）

### 3.1 已有能力

- 同步服务（`services/sync-api`）：
  - 笔记（Markdown）接口：`/api/v1/notes/push|push-batch|list|get|changes|ack`（见 `services/sync-api/internal/handlers/notes_handler.go`）。
  - 附件上传接口：`/api/v1/uploads/file`（见 `services/sync-api/internal/handlers/upload_handler.go`）。
  - 文件落盘路径：`{UploadPath 或 ./data/uploads}/users/{userKey}/...`，`userKey` 为 `username` 清洗后字符串，缺失则用 `user_id`。
- 桌面端（`apps/desktop/frontend`）：
  - 已具备本地目录读写（`window.electronAPI.*`）与部分笔记同步逻辑（`src/store/noteFiles.ts`、`src/components/NotebookTab.tsx`）。

### 3.2 主要缺口（导致“不稳妥”的典型来源）

- 云端缺少“文件管理”的完备接口（尤其是：下载附件、删除/回收站、重命名、列出完整文件树、元数据/版本）。
- 现有笔记同步以“推送 + 拉取变化”为主，对“重命名/删除/附件下载”等覆盖不足，且冲突处理对用户不够可控。

因此，本方案会新增一组“云端文件空间 API”，用于支撑云端文件管理与手动同步；原 `/notes/*` 可先保持兼容，后续再决定是否统一迁移到新 API。

## 4. 核心概念

- **本地同步目录**：用户在客户端选择的目录（当前可复用 `SETTING_KEYS.NOTEBOOK_DEFAULT_DIR` 作为默认目录）。
- **云端用户根目录**：服务端为当前用户隔离出的文件根，形如：
  - `./data/uploads/users/{userKey}/`（推荐 `use_data=true`）
  - 或 `./uploads/users/{userKey}/`
- **回收站**：云端侧的软删除区，删除操作不直接 `unlink`，而是移动到回收站并记录原路径等信息。
- **备份**：当用户选择“强制替换”覆盖云端时，覆盖前把被覆盖的云端旧文件移动到备份区，保留可恢复副本。

## 5. 客户端功能设计

### 5.1 信息架构

在桌面端新增“手动同步”能力，推荐落在「记事本」Tab 内（与用户心智一致）：

- 「记事本」页顶部工具栏新增：
  - `云端文件`：打开云端文件管理抽屉/弹窗（文件树 + 回收站）。
  - `手动同步`：打开同步面板（上传/下载/冲突处理/进度）。

同时在「设置」中补充与手动同步相关的配置：
- 本地同步目录（已存在/复用）：选择目录。
- 云端文件空间：开关（仅决定是否显示云端管理与同步按钮，不做自动同步）。
- 默认策略：下载/上传遇到冲突时的默认行为（默认为“每次询问”）。

### 5.2 云端文件管理（当前用户）

#### 5.2.1 文件树视图

- 展示：云端用户根下的目录树（可懒加载）。
- 筛选：按类型筛选（`md`、图片、其他附件）。
- 搜索：按文件名搜索（可先客户端过滤，再扩展服务端搜索）。

#### 5.2.2 文件操作

- 查看/预览：
  - 文本（如 `.md`、`.txt`）：打开在线预览/编辑器（读取云端内容）。
  - 图片：预览图（通过云端下载 URL）。
  - 其他文件：显示元信息（大小/修改时间/sha256 可选），提供“下载”。
- 编辑（文本类）：
  - 保存时写回云端：调用“写文件”接口。
  - 保存前若检测到云端已变化：提示冲突（见 5.4）。
- 重命名/移动：
  - 通过“重命名”接口完成。
- 删除：
  - 默认进入回收站（软删除），UI 文案明确“可在回收站恢复”。

#### 5.2.3 回收站

- 列表：展示回收站条目（原路径、删除时间、大小）。
- 操作：
  - 还原（恢复到原路径；若原路径已有同名文件则提示冲突并提供“强制还原（覆盖 + 备份）”）。
  - 彻底删除（不可恢复，需二次确认）。
- 自动清理策略（默认）：保留 30 天或保留最近 N 条，超出后自动清理（服务端执行）。

### 5.3 手动同步（上传/下载）

#### 5.3.1 下载到本地同步目录

- 入口：手动同步面板 -> `从云端下载`
- 模式：
  - 选择云端文件（多选）下载到本地同步目录对应相对路径。
  - 下载全部（云端根递归下载）。
- 行为：
  - 若本地不存在：直接下载写入。
  - 若本地存在且内容相同：跳过。
  - 若本地存在且内容不同：触发冲突提示（见 5.4）。

#### 5.3.2 上传本地文件到云端

- 入口：手动同步面板 -> `上传到云端`
- 模式：
  - 选择本地文件（多选）上传到云端保持相对路径。
  - 上传全部（本地同步目录递归上传）。
- 行为：
  - 若云端不存在：直接上传。
  - 若云端存在且内容相同：跳过。
  - 若云端存在且内容不同：触发冲突提示（见 5.4）。
  - 若用户选择“强制替换”：服务端在覆盖前自动备份旧版本（见 6.3）。

### 5.4 冲突提示（最小可用交互）

#### 5.4.1 冲突定义

当“写入目标端”会覆盖一个已存在且**与当前内容不同**的文件时，判定冲突。

“不同”的判定建议分两级：
- 快速判定：`size_bytes` 或 `mtime_ms` 不同则视为可能冲突。
- 精确判定：按需计算 `sha256`（服务端/客户端二选一，优先服务端提供 meta）。

#### 5.4.2 弹窗内容

必须提供：
- 文件路径（相对路径）
- 本地版本信息（mtime/size，可选 hash）
- 云端版本信息（mtime/size，可选 hash）
- 操作按钮：
  - `跳过`（不覆盖）
  - `强制替换`（覆盖对端；若覆盖云端则云端先备份）

可选扩展（不作为本轮验收要求）：
- `保留双方`（云端生成副本或本地生成副本）
- `对比差异`（仅对文本文件）

## 6. 服务端设计（云端文件空间）

### 6.1 存储布局

在现有用户隔离根目录基础上，新增保留目录（默认隐藏，不在普通列表中返回）：

```
{BASE}/users/{userKey}/
  ... 用户业务目录（与本地同步目录保持一致的相对路径）
  .xpaste-trash/
    items/
      {trash_id}/
        file              # 被删除的文件内容（原样保存）
        meta.json          # 原路径/删除时间/size/hash/mtime 等
  .xpaste-backups/
    {YYYYMMDD}/
      {original_rel_path}__{ts}__{op}.bak
```

说明：
- `BASE` 对应：
  - `use_data=true` 时：`./data/uploads`（与现有笔记同步一致）
  - 否则：`UPLOAD_PATH`（默认 `./uploads`）
- `.xpaste-trash` 与 `.xpaste-backups` 只作为实现细节；API 默认不暴露为普通目录项，避免污染用户目录树。

### 6.2 路径与权限

- 所有 API 必须基于现有 JWT 鉴权中间件（`middleware.AuthMiddleware`）。
- 路径参数统一使用“相对用户根”的相对路径（例如 `Work/meeting.md`）。
- 服务端必须做路径清洗与禁止目录穿越（`..`、绝对路径等）。
- 默认拒绝直接访问保留目录（`.xpaste-trash`、`.xpaste-backups`），仅允许通过专门的回收站/备份接口访问。

### 6.3 强制替换时的云端备份

当客户端上传/保存选择“强制替换”且目标云端已存在时：

1. 服务端生成备份文件名（包含时间戳与操作来源）；
2. 将“被覆盖的旧文件”移动到备份目录（同分区移动优先，失败则 copy + remove）；
3. 再写入新文件内容；
4. 返回响应中带回 `backup_path`（可用于未来“回滚”功能）。

默认保留策略（可配置）：
- 备份保留 30 天；
- 或每个原始路径最多保留最近 20 个备份（超出先删旧）。

### 6.4 回收站（软删除）

删除文件时默认不物理删除：

1. 生成 `trash_id`（UUID 或 `{ts}-{rand}`）；
2. 创建目录 `.xpaste-trash/items/{trash_id}/`；
3. 将原文件移动到该目录下固定名 `file`；
4. 写入 `meta.json`：
   - `trash_id`
   - `original_path`
   - `deleted_at_ms`
   - `mtime_ms`
   - `size_bytes`
   - `sha256`（可选，若计算成本可接受）

还原时：
- 若 `original_path` 位置为空：直接移动回去。
- 若已存在同名文件：作为冲突处理：
  - 默认返回 `409 Conflict`，由客户端提示用户；
  - 若客户端选择“强制还原”：对现有文件先做备份（同 6.3），再覆盖。

彻底删除时：
- 删除回收站条目目录（不可恢复）。

自动清理（可配置）：
- 回收站保留 30 天，后台清理过期条目；
- 或回收站总大小上限（例如 2GB），超出按最旧优先清理。

## 7. API 设计（草案）

所有接口前缀：`/api/v1/cloud-files`（名称可调整；此处为便于与现有 `/notes` 区分）。

### 7.1 文件与目录

| 功能 | 方法 | 路径 | 说明 |
|---|---|---|---|
| 列表（目录） | GET | `/tree?path=&recursive=0` | 返回目录下条目（含 meta）；`path` 为空表示根 |
| 元信息（文件） | GET | `/meta?path=` | 返回 `size/mtime/sha256?` |
| 下载（文件） | GET | `/file?path=` | 二进制流；响应头带 meta（`X-File-*`） |
| 写入（文本） | PUT | `/text` | `{ path, content, if_match_hash? , mode? }` |
| 上传（二进制） | POST | `/upload?path=` | multipart `file`；`mode=force` 时启用备份覆盖 |
| 重命名/移动 | PATCH | `/rename` | `{ from_path, to_path, mode? }` |
| 删除（进回收站） | DELETE | `/file?path=&trash=1` | 默认 `trash=1`；`trash=0` 走物理删除（管理员/高级设置） |

建议的通用响应结构与现有保持一致（`success/message/data`）。

`mode` 取值建议：
- `safe`（默认）：存在冲突则返回 `409`；
- `force`：允许覆盖；覆盖前备份；

### 7.2 回收站

| 功能 | 方法 | 路径 | 说明 |
|---|---|---|---|
| 列表 | GET | `/trash` | 返回回收站条目列表（分页可选） |
| 还原 | POST | `/trash/restore` | `{ trash_id, mode? }`；`mode=force` 允许覆盖并备份 |
| 彻底删除 | DELETE | `/trash/item?trash_id=` | 永久删除回收站条目 |

### 7.3 冲突（统一错误码）

当服务端拒绝覆盖时返回：
- HTTP `409`
- body：
  - `success=false`
  - `message="Conflict"`
  - `data`: `{ path, local_suggest?, remote: { mtime_ms, size_bytes, sha256? } }`

客户端据此弹窗提示并可在用户选择后以 `mode=force` 重试。

## 8. 同步策略（手动模式）

### 8.1 下载（云端 -> 本地）

步骤：
1. 调用 `/tree` 获取云端清单（可递归）。
2. 对每个条目在本地同步目录下计算目标路径并检查是否存在。
3. 需要下载的文件：
   - 不存在：下载写入；
   - 存在：对比 meta/hash，冲突则提示；用户选择“强制替换”时，可在本地先备份再覆盖。

### 8.2 上传（本地 -> 云端）

步骤：
1. 客户端扫描本地同步目录（或用户选中的文件集合）。
2. 对每个文件先查云端 `/meta`：
   - 不存在：直接上传；
   - 存在：对比 meta/hash，冲突则提示；
3. 用户选择“强制替换”：
   - 调用上传接口并携带 `mode=force`，服务端覆盖前自动备份旧版本。

## 9. 默认策略（用于实现验收）

为避免过度复杂，本轮实现建议固定默认行为：

- 删除：默认进入回收站。
- 冲突：默认弹窗询问，不做自动覆盖。
- 强制替换：
  - 覆盖云端：云端必备份；
  - 覆盖本地：本地建议也做备份（可在本地同步目录下创建 `.xpaste-local-backups/`，实现可选）。

## 10. 兼容性与迁移

- 现有 `/api/v1/notes/*` 与 `/api/v1/uploads/file` 继续保留，以避免影响现有记事本功能。
- 新的“云端文件空间 API”面向手动同步与云端管理页面，逐步替换旧同步逻辑。
- 后续可选：
  - 让 `/notes/push` 内部调用新 API 的“写文本”能力；
  - 或直接在客户端改为走新 API，统一云端文件的行为（特别是删除/重命名/回收站/备份）。
